# Previous-month FX for household spending

**Goal.** Give each household event one reproducible value in the workspace currency. For this household that currency is ILS. A purchase billed in a foreign currency uses the previous completed calendar month’s average. The converted amount expresses the household’s budgeting convention. The acquisition cost of dollars in the bank account is unknown.

**Scope.** Bank imports, manual and recurring entries, classification, spending reports, export, read-only reporting tools, and shared settlements. Broker-provided portfolio valuations retain their own dates and methodology. Build against the current default branch and reconcile the open [PR #164](https://github.com/zemser/HomeBooks/pull/164) before assigning migration numbers. The older [Max FX specification](../../max-fx-normalization-spec.md) describes the statement formats and the same-month policy being superseded.

**Implementation order.** Deliver the following tasks behind a per-workspace rollout switch. Use the repository’s TypeScript, Drizzle, Postgres, and existing review-test harness. Schema changes are additive during rollout.

## 1. Define the amount that every consumer reads

- [ ] In `src/features/currency/monthly-rates.ts` resolve the immediately preceding calendar month from the source’s local transaction date. Use December of the prior year for a January purchase. For recurring payments use the date of the generated occurrence. Later booking, import, classification, or allocation dates never change the selected month.
- [ ] In `src/db/schema.ts` and a migration, give transactions and generated entries an explicit valuation state (recorded, converted, pending, or retained legacy), policy version, reference month, and reference to the rate used. Keep the existing original, settlement, and normalized amounts, currencies, and applied numeric rate. A pending amount is unknown. During compatibility rollout, any stored zero sentinel must be gated by state everywhere. Genuine zero amounts remain valid.
- [ ] Choose the bank’s posted workspace-currency amount first, including the bank’s own conversion. Otherwise convert the **settlement** amount and currency. An unknown original currency may stay unknown. If the charged currency itself is ambiguous, keep it pending for review. Preserve Cal’s explicit fields. Max original-currency inference is optional descriptive metadata and can retain its own same-month evidence.
- [ ] Use decimal arithmetic, retain the applied rate at database precision, round the resulting ILS amount once to agorot, and allocate rounding remainders deterministically. Keep debit/credit direction under existing conventions. Never hard-code ILS for other workspaces. Preserve supported direct and inverse pairs and keep unsupported pairs visibly pending.
- [ ] Pin the contract in `tests/review/max-fx-normalization.test.ts`. A November USD 100 purchase at a fixture October average of 3.088 gives ILS 308.80. An equal two-person split gives ILS 154.40 each. A November rate arriving later changes neither amount. An ILS 62.05 statement charge remains ILS 62.05 even if its original currency is unknown. Cover January rollover, inverse rates, missing months, and a legitimate zero.

## 2. Replace hand-written seeds with a month cache

- [ ] Reuse `exchange_rate_monthly` keyed by the **observation month**, currency pair, and source. October observations stay keyed as October. Record provider, series, retrieval time and calculation version. Persist input observation count when aggregating. Keep historical migrations runnable and trusted seed data usable after validating units and provenance. Remove recurring seed-file maintenance from `scripts/dev-local.mjs` once empty-database bootstrap is proven.
- [ ] Add a server-only Bank of Israel adapter under `src/features/currency/`. First verify the official completed-month average export against existing USD and JPY fixtures. Prefer that series when its definition and precision match. Otherwise request the historical daily representative series for complete months, average the distinct published daily observations, and convert quoted units to units of one (JPY is quoted per 100). Validate series, pair, dates, currency units, positivity, and completeness. Reject truncated, duplicate-conflicting or partial responses. Do not pad nonpublication days. Confirm applicable API data reuse terms before enabling production distribution. [BoI historical API](https://www.boi.org.il/media/qoonuupn/extracting-representative-exchange-rates-from-the-new-series-database.pdf) · [BoI monthly exports and currency units](https://www.boi.org.il/en/economic-roles/financial-markets/exchange-rates)
- [ ] Collect distinct missing pair/month keys across a workbook, recurring generation, or history batch. Enqueue durable requests with a unique key. A server worker claims batches, groups adjacent months per series, fetches outside database transactions, and writes through a restricted database identity. The application may request supported keys but cannot supply rates or write the global cache. Only dates and currency identifiers leave the app.
- [ ] Dispatch on demand. Run a scheduled drain of outstanding requests for unattended retries with backoff and a bounded timeout. No daily market-data subscription is required. On success, queue pending-row reconciliation for affected workspaces. Retry failed reconciliations independently of successful rate retrieval. Treat a provider revision as a new auditable version and preserve already applied valuations. Report oldest outstanding month, pending count and last failure.
- [ ] Test with recorded responses, including JPY, a month spanning holidays, malformed data, duplicate requests, provider outage and recovery. A fresh DB with **no FX seed rows** must import, fetch, value, and report without running a seed migration by hand. Keep live-provider verification separate from deterministic CI.

## 3. Connect imports, recurring payments, and household views

- [ ] Update `src/features/imports/parse-bank-workbook.ts` and `persistence.ts` to use the same valuation function. Preview reads cached data and can enqueue missing months. Save rechecks the cache, stores the applied snapshot, and can accept a pending charge. Indicate if a rate arrived between preview and save. Neither path waits on an external call inside a DB transaction.
- [ ] Fix identity **before** history repair. Version the import identity in `persistence.ts`. Use stable statement fields and explicit bank currency where available. Exclude inferred currency, rates and normalized amounts. Preserve legacy hashes and match old rows through a compatible identity/alias. Test overlapping exports with different checksums where the Cursor original currency moves from unknown to USD. Detect ambiguous matches, including two genuine identical purchases, and send them for review instead of merging them.
- [ ] Manual entries entered in workspace currency continue at face value in `src/features/manual-entries/service.ts`. In `src/features/recurring/service.ts`, replace the foreign rate-of-one branch for generated occurrences. Preserve overrides when regenerating. Permit classification and payer assignment while FX is pending. A workspace-currency split becomes payable only after a recorded valuation exists.
- [ ] Update `src/features/reporting/expense-events.ts`, monthly and annual reports, budgets/spending summaries, home views, CSV exports and read-only MCP report responses to consume the stored valuation. Return both the known workspace total and pending counts/amounts grouped by source currency. Example: “₪4,210 recorded · US$100 awaiting conversion.” Keep different pending currencies separate. Export the same amounts and expose pending status and the reference month wherever row detail is exported.
- [ ] In `src/features/shared-settlements/service.ts` use the same stored event amount for splitting. Freeze agreed repayments. For an attributable full refund, reverse the original recorded shekel amount. For a linked partial refund reverse proportionally, allocating the final rounding remainder to the last refund. Use an explicit original-transaction link or a confirmed match. An unmatched credit follows its own date and is eligible for later reconciliation. Currency exchanges between household accounts remain transfers; independently identified fees can count as expenses.
- [ ] Test through import save, recurring generation, reporting, export and settlement entry points. Simulate an unavailable provider, user classification, later automatic repair, an overlapping statement, and a subsequent worker retry. Assert one purchase, consistent report/export/split amounts, preserved user inputs, and zero writes on the last retry.

## 4. Migrate history without silently changing household balances

**Recommended default.** Preserve trustworthy amounts already shown to the household. Repair missing or demonstrably artificial values. Offer a separate, explicit restatement for users who want all past reference-valued spending on the new convention. Either choice preserves statement facts and the original audit record.

| Existing data | Default treatment |
|---|---|
| Bank posted the workspace-currency amount, manual base-currency entry, or documented user override | Retain the amount. Identify it as recorded or overridden. |
| Valid foreign conversion using the former transaction-month policy | Label it as a legacy conversion and retain its rate. Preview its previous-month equivalent and effect on monthly totals before any optional restatement. |
| Imported missing rate, zero sentinel, foreign rate-of-one placeholder, or affected recurring occurrence | Select by source and currency evidence across all importers, independent of section text. Fetch the required previous month and repair automatically when the source is unambiguous and the row has no protected allocation or split. |
| Fixed, settled, or otherwise user-adjusted split or allocation affected by a proposed change | Preserve amount, event ID, allocations, split definition, participants, and settlement status. Show the proposed difference for explicit reconciliation. Record any approved adjustment separately with its effective date. |
| Unknown provenance, unsupported pair, ambiguous duplicate, or inconsistent statement fields | Keep the source record and surface the reason for review. Never infer a historical placeholder from a numeric zero or rate of one alone. |

- [ ] Extend `scripts/renormalize-imported-fx.ts` with a read-only dry run as the default. Produce per-workspace/month counts by category, available/missing rate keys, old/new totals, pending currencies, protected records, and suspected duplicates. Snapshot the candidate IDs, prior values and versions. Run the inventory before changing reports or dropping previous logic.
- [ ] In `src/features/currency/backfill-imported-fx.ts` repair eligible records in resumable batches. Use the settlement fields already stored. Apply the valuation, change audit and derived event/allocations in the same transaction. Lock or condition on the inventoried version; recheck protections so a concurrent classification or split edit wins. Persist run ID, reason, policy version and before/after values. Selecting pending rows must include Cal rows without Hebrew section text.
- [ ] Run a staging rehearsal on a representative snapshot and one pilot workspace. Compare report, export, monthly allocation, and member balance deltas against the dry run. Verify protected rows by ID, amounts, recipients, and settlement status. An unchanged second run must produce zero writes. Test a crash midway and resume. Roll back via the run’s audit records only where the post-migration version still matches; send later user edits for review.
- [ ] Enable new writes workspace by workspace. Report rows repaired, rows retained under the old policy, differences awaiting review and unresolved rate requests. If the household chooses uniform retrospective reporting, present the dated restatement preview separately and require explicit selection before applying it. Keep formerly exported figures explainable through the audit.
